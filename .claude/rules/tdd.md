# TDD Rule

**이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계 생략, 순서 변경, 예외 창작 금지.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없거나 침묵하는 부분에만 적용한다.

## 적용 기준

### TDD 필수

- 비즈니스 로직
- API (핸들러, 라우팅, 요청/응답 처리)
- 유틸 / 순수 함수
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성)

### TDD 불필요

- 타입 정의 (`type`, `interface`)
- 설정 파일 (`vite.config.ts`, `tsconfig`, ESLint 등)
- 순수 UI (스타일링, 레이아웃, 마크업만 있는 컴포넌트)
- SQL (스키마, 마이그레이션, 쿼리 정의)

대상이 애매하면 **TDD를 적용한다.**

## RED-GREEN-REFACTOR

### 1. RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 묶지 마라.
- 테스트를 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 테스트는 테스트가 아니다.
- 실패 이유는 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 오타, 잘못된 셋업으로 실패한 것은 RED가 아니다. 테스트를 고쳐 올바른 이유로 실패시켜라.

### 2. GREEN — 통과시키는 최소 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 다음 테스트가 요구하지 않는 기능, 분기, 옵션, 추상화를 미리 넣지 마라.
- **신규 + 기존 테스트 전체**를 실행해 모두 통과하는지 확인한다.

### 3. REFACTOR — 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 수행한다.
- 모든 테스트가 **green을 유지**해야 한다. 변경할 때마다 실행한다.
- **새 동작 추가 금지.** 새 동작이 필요하면 RED로 돌아가라.

### 4. 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 동작이 끝날 때까지 반복한다.

## 삭제 강제 규칙

- 테스트 전에 프로덕션 코드를 먼저 작성했다면 **그 코드를 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 해당한다.
- 삭제 후에는 테스트가 요구하는 만큼만 새로 작성한다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드일수록 테스트 작성 비용이 거의 0이다. 단순한 코드가 가장 먼저 회귀한다. |
| "나중에 테스트 추가하겠다" | 나중에 쓴 테스트는 구현을 따라 쓴 확인용이다. 즉시 통과하므로 아무것도 증명하지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. 시간이 없을수록 RED-GREEN이 빠르다. |
| "삭제하면 낭비다" | 매몰비용 오류다. 검증되지 않은 코드를 유지하는 비용이 재작성 비용보다 크다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 삭제 비용도 0이다. |
