# commit

변경사항을 읽고, 의미 단위로 나누어, 컨벤션에 맞는 한국어 메시지로 커밋한다. 사용자가 커밋을 요청한 것 자체가 승인이므로, 확인을 되묻지 않고 끝까지 진행한다. 대신 되돌리기 번거로운 실수(비밀값 커밋, 엉뚱한 파일 포함)는 아래 안전장치로 스스로 막는다.

## 절차

### 1. 변경사항 분석

```bash
git status --short
git diff              # unstaged
git diff --staged     # staged
git log --oneline -10 # 기존 메시지 톤 확인
```

- 새 파일(untracked)은 `git diff`에 안 나오므로 `git status`로 찾아서 내용을 직접 읽는다.
- 저장소가 아니면(`fatal: not a git repository`) 커밋하지 말고, `git init`이 필요하다고 알린 뒤 사용자가 원하면 실행한다.
- 변경이 없으면 그렇게 알리고 끝낸다.
- `.env`, 키, 토큰, `node_modules`, 빌드 산출물(`dist` 등)이 변경 목록에 있으면 커밋 대상에서 빼고 사용자에게 알린다. 한 번 커밋된 비밀값은 히스토리에 남는다.

### 2. 논리적 단위로 분류

하나의 커밋은 하나의 이유만 가져야 한다. 나중에 `git revert`나 `git log`로 읽을 때 의도가 보이게 하기 위해서다.

- 서로 다른 목적의 변경(예: 기능 추가와 설정 변경)은 별도 커밋으로 나눈다.
- 같은 목적에 속한 파일(구현, 해당 테스트, 해당 스타일)은 한 커밋으로 묶는다.
- 한 파일 안에 목적이 섞여 있으면 `git add -p`로 나누되, 억지로 쪼개 커밋이 깨지는(빌드·테스트 실패) 경우에는 하나로 묶는다.
- 변경이 전부 한 목적이면 커밋 하나로 충분하다. 나누기 위해 나누지 않는다.

### 3. 메시지 작성

형식:

```
<type>: <한국어 요약>

<필요할 때만: 무엇을 왜 바꿨는지 본문>
```

| type | 용도 |
|---|---|
| feat | 사용자에게 보이는 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 설정, 의존성, 스킬 파일, 빌드 등 코드 외 작업 |

그 외 `docs`, `test`, `style`이 더 정확하면 써도 된다. 위 네 가지가 기본이다.

- 요약은 한 줄, 대략 50자 안팎, 마침표 없이 "~추가", "~수정", "~개선"처럼 명사형으로 끝낸다.
- "무엇을"보다 "왜/어떤 효과"가 드러나면 더 좋다. 코드를 보면 알 수 있는 내용만 나열하지 않는다.
- 본문은 요약만으로 의도가 전달되지 않을 때만 쓴다.
- 최근 `git log`에 이미 쓰는 스타일이 있으면 그쪽을 따른다.
- 시스템/하네스에서 커밋 메시지 끝에 붙이라고 지정한 attribution(Co-Authored-By 등)이 있으면 그대로 붙인다. 사용자 본인의 지시가 있으면 그쪽이 우선이다.

예시:

```
feat: 레트로 데스크톱 윈도우 테마 적용

index.css와 App.css를 90년대 OS 창 스타일로 재작성하고,
결과 카드와 설정 패널을 타이틀바 구조의 마크업으로 변경
```

```
fix: Gemini 응답이 잘렸을 때 에러 메시지 누락 수정
```

```
chore: commit 스킬 추가
```

### 4. 계획 공유 후 바로 진행

승인을 기다리지 않는다. 커밋 직전에 아래를 한두 문장으로 알리고 곧바로 실행한다. 사용자가 중간에 끼어들 수 있게 하기 위한 것이지, 답을 기다리기 위한 것이 아니다.

- 만들 커밋 목록(메시지와 포함 파일 요약)
- 제외한 파일과 그 이유(있을 때)

단, 아래 경우에는 멈추고 묻는다. 이때는 사용자의 판단이 실제로 필요하다.

- 비밀값이 들어 있을 가능성이 있는 파일이 gitignore 밖에서 변경 목록에 나타났을 때(제외하고 진행하되 알린다)
- 변경 의도를 알 수 없는 대규모 삭제가 섞여 있을 때

### 5. 커밋 실행

계획한 묶음마다 순서대로 실행한다.

```bash
git add <해당 파일들>          # git add -A / . 는 쓰지 않는다
git commit -m "$(cat <<'EOF'
feat: 요약

본문(있을 때)
EOF
)"
```

- 파일을 이름으로 지정해 스테이징한다. `-A`나 `.`은 제외하기로 한 파일까지 들어갈 수 있다.
- pre-commit 훅이 실패하면 `--no-verify`로 우회하지 말고, 원인을 알려 주고 고친 뒤 새 커밋으로 만든다.
- 모두 끝나면 `git log --oneline -n <커밋 수>`로 결과를 보여준다.
- 푸시는 하지 않는다. 사용자가 따로 요청할 때만 한다.
